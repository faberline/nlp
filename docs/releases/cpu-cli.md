# CPU CLI packages

The build workflow produces one archive per native target: Apple Silicon macOS, Intel macOS, and Windows x64 MSVC. It does not combine the macOS files. Each archive contains `nlp`, or `nlp.exe` on Windows, the tracked data notices, and `build-info.json`. The build uses the default CPU feature set. These packages contain the CPU rules engine and embedded lexicon. Model options remain in the CLI. Running a model needs an opt-in build with a model backend enabled. These default packages do not enable optional backends or include model weights.

Each runner collects dependency notices from locked target metadata, uploads its archive and checksum, downloads them again, verifies file inventory and source metadata, extracts the archive, and compares all seven commands with the legacy binaries on synthetic data. The Windows build requests `+crt-static`. Its PE import table and delay imports must contain only reviewed system DLL names and no dynamic Microsoft C runtime. The macOS build records `otool -L` output and rejects non-system libraries. The archive includes this import report. The gate requires every matrix job to succeed. These checks must run on GitHub before native support can be claimed. Import inspection does not prove behavior on every supported OS version or detect every possible runtime load. No minimum OS version is asserted.

The tag workflow calls the same build and waits for its gate. It checks that `v<workspace version>`, the tag target, the checkout, and all three artifact manifests agree. It rejects an existing release. It creates `SHA256SUMS` and creates a release only after preflight succeeds. It never updates an existing release. Tag creation and publication require the owner's permission.

The dependency receipt lists license expressions and available notice files for the locked Cargo dependency closure. It includes build dependencies as a conservative superset. The source-lexicon receipt identifies embedded data inputs; it is separate from the packaged Cargo dependency receipt, which does not establish provenance for every embedded input. Review the tracked data notices and exact archive before formal release. No separate approval file is required by this workflow.

The workflow uses standard GitHub-hosted runners. [GitHub's runner documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists the macOS ARM and Intel labels and explains the public-repository billing terms. Native candidate workflow checks have passed, but those results do not establish that a later main revision, release tag, or published archive has passed. Verify checks and downloads for the exact release source before claiming formal release support.
