# CPU CLI packages

The build workflow produces one archive per native target: Apple Silicon macOS, Intel macOS, and Windows x64 MSVC. It does not combine the macOS files. Each archive contains `nlp`, or `nlp.exe` on Windows, the tracked data notices, and `build-info.json`. The build uses the default CPU feature set. The model options remain in the CLI, but model weights and optional model backends are not in these packages.

Each runner collects dependency notices from locked target metadata, uploads its archive and checksum, downloads them again, verifies file inventory and source metadata, extracts the archive, and compares all seven commands with the legacy binaries on synthetic data. The Windows build requests `+crt-static`. Its PE import table and delay imports must contain only reviewed system DLL names and no dynamic Microsoft C runtime. The macOS build records `otool -L` output and rejects non-system libraries. The archive includes this import report. The gate requires every matrix job to succeed. These checks must run on GitHub before native support can be claimed. Import inspection does not prove behavior on every supported OS version or detect every possible runtime load. No minimum OS version is asserted.

The tag workflow calls the same build and waits for its gate. It checks that `v<workspace version>`, the tag target, the checkout, and all three artifact manifests agree. It rejects an existing release. It creates `SHA256SUMS` and creates a release only after preflight succeeds. It never updates an existing release. Tag creation and publication require the owner's permission.

The collected dependency receipt lists license expressions and available notice files. It includes build dependencies as a conservative superset. A package with no notice files needs review; absence does not alone prove a distribution violation. The exact WordNet input and some corpus and upstream notice details remain unknown. Review the available evidence and include all applicable notices before publication. Review the exact archive and current commit; the machine-generated receipt alone does not establish legal completeness. No separate approval file is required by this workflow.

The workflow uses standard GitHub-hosted runners. [GitHub's runner documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists the macOS ARM and Intel labels and explains the public-repository billing terms. Native runners, action availability, toolchains, and downloadable archives have not yet been verified by an actual workflow run.
